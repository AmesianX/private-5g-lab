# 시뮬레이션과 실물의 간극 — 무엇이 달랐고 어떻게 메웠나

2026-10-15. 기준은 **실물 단말**이다. 모의 UE(OAI nr-UE)와 스크립트가 실물과 다르게
동작하면 그건 모의 쪽을 고칠 일이지, 실물을 맞출 일이 아니다.

이 문서는 결론만이 아니라 **틀렸던 순서대로** 적는다. 어떤 증상을 보고 무엇을 의심했고,
그게 왜 틀렸는지가 다음 사람에게는 결론보다 쓸모 있다.

## 간극 1 — 코덱

스크립트는 G.711(PCMU/PCMA)을 제시했다. 스크립트끼리는 서로 받아 주니 몇 달 동안
문제가 없었다. 실물 단말은 `488 Not Acceptable Here` 로 끊는다. IMS 음성은
**AMR / AMR-WB** 다. 모의 UE 가 아무 코덱이나 받아 준다는 것은 모의 UE 의 성질이지
망의 성질이 아니었다.

## 간극 2 — 신뢰성 임시응답(PRACK)

실물 단말은 `183 Session Progress` 를 `Require: 100rel` 로 보낸다. PRACK 를 주지 않으면
183 을 세 번 재전송하다 `500` 으로 끝난다. 스크립트 착신부는 애초에 183 을 보내지
않았으므로 발신부에 PRACK 구현이 없어도 아무 문제가 없었다.

## 간극 3 — QoS 전제조건

전제조건을 선언하지 않으면 단말이 UPDATE 를 기다리느라 벨을 울리지 않는다.
SDP 에 `a=curr:qos ... sendrecv` 와 `a=des:qos mandatory ...` 로 **이미 충족**을
선언하면 바로 `180 Ringing` 이 온다. 전용 베어러를 따로 세우지 않는 우리 랩에서는
이게 사실에 맞는 선언이다.

## 간극 4 — SDP 응답이 오는 위치

전제조건 방식에서는 **SDP 응답이 183 에 실려 온다. `200 OK` 에는 없다.**
200 OK 만 보고 미디어를 찾으면 `착신측 미디어 None:None` 이 되고, 그 자리에서 BYE 가
나간다. 로그에는 "통화 성립 ✅" 이 찍히므로 **성공으로 오인하기 쉽다.**

그리고 PRACK 에 대한 `200 OK` 를 통화 응답으로 착각하면 벨이 울리는 중에 끊긴다.
2xx 를 받으면 **CSeq 의 메서드가 INVITE 인지** 봐야 한다.

## 간극 5 — 공개 신원을 IMSI 로 만들었다

스크립트는 IMPU 를 `sip:<IMSI>@<realm>` 으로 쓰고 착신 대상도 IMSI 형식으로 걸었다.
실물 단말은 **번호 기반 IMPU**(`sip:<MSISDN>@<realm>`)로 등록하고 번호로 걸린다.
IMSI 형식으로 INVITE 하면 I-CSCF 가 이렇게 답한다.

```
SIP/2.0 500 Server error on LIR select next S-CSCF
```

IMPI 는 IMSI 기반이 맞지만 IMPU 는 아니다(TS 23.003). 등록이 성공한다고 해서
그 신원으로 걸 수 있는 것도 아니다.

## 간극 6 — `500 LIR select next S-CSCF` 는 LIR 실패가 아니었다

번호로 고쳐도 **전체 모드(both)에서는 같은 500 이 계속 나왔다.** 별도 프로세스로
착신·발신을 나눠 돌리면 통했다. 그래서 LIR·PyHSS·S-CSCF 배정을 한참 뒤졌는데,
세 가입자 모두 `scscf` 가 정상으로 들어가 있었다.

원인은 전혀 다른 데 있었다. 전체 모드가 **자기만의 INVITE·응답 코드를 따로 들고
있었고, 그 착신부는 UDP 만 들었다.** 코덱과 전제조건을 넣으면서 SDP 가 331 → 606
바이트로 커졌고, INVITE 가 1300바이트를 넘자 P-CSCF 가 **TCP 로 전환**했다.
착신부가 그 TCP 연결을 받지 못하니 응답이 없었고, 발신측에는 I-CSCF 의 일반 오류인
500 이 돌아왔다. 메시지 문구와 실제 원인이 전혀 달랐던 경우다.

고친 방법은 증상을 막는 게 아니라 **중복을 없애는 것**이었다. 전체 모드를 지우고
실물로 검증된 `run_callee`/`run_caller` 하나만 쓰게 했다(134줄 삭제). 경로가 둘이면
한쪽만 실물과 어긋나는 일이 반드시 다시 생긴다.

## 간극 7 — TCP 는 스트림이다

TCP 로 INVITE 를 받게 되자 이번에는 `발신측 미디어 None:None` 이 떴다. `recv()` 를
한 번만 불러서 헤더만 읽고 본문이 덜 온 것이다. UDP 에서는 한 데이터그램이 곧 한
메시지라 드러나지 않던 문제다. `Content-Length` 만큼 채워 읽도록 `recv_sip_tcp()` 를
만들어 UA 의 모든 TCP 수신 경로에 넣었다.

## 정렬 후 실측

| 경로 | 결과 |
|---|---|
| 모의 UE ↔ 모의 UE (`both 10`) | RTP 499/497 · 499/499, BYE 200 OK |
| 모의 UE → 실물 폰 (`caller 15`) | RTP 748 송신 / 103 수신, BYE 200 OK |

실물 쪽 수신 패킷이 적은 것은 고장이 아니라 **DTX**다. 차폐함 안이 조용하니 단말이
편안잡음 프레임만 띄엄띄엄 보낸다. 15초에 100개 남짓이면 정상 범위다.

## 남은 간극

- 모의 UE 는 DTX 를 흉내 내지 않는다. 묵음 구간에서도 50 pps 를 꽉 채워 보낸다.
- 모의 UE 는 IPsec 을 쓰지 않는다. 실물은 P-CSCF 와 IPsec SA 위에서 SIP 를 주고받는다.
- ~~영상통화(5QI 2)는 실물 단말로 아직 확인하지 않았다.~~ 같은 날 확인했다 — video RTP
  송신 332 / 수신 2697(20초), 단말이 초당 약 135 패킷을 올려보낸다. 우리 쪽은 더미라
  단말 화면에는 "상대방 영상 준비 중" 이 남는다. [[mms-and-video.md]], 화면 증거
  `docs/screenshots/11-영상통화-수신.png`·`12-영상통화-연결.png`.
- 모의 UE 로는 **MMS 를 시험할 수 없다**(데이터망 HTTP GET 이 필요하다). 실물 전용이다.
